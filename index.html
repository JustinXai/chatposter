0先记住这一层的分工

这一页 = 渲染层。它不负责拿数据、也不负责思考，只负责把结构化结果画好看。

两个参考仓库都是同一种三层切法：

WeChatDaily
wechat.py export 导出 Markdown → AI Coding Agent 读 Skill 分析 → 写 analysis_*.json → render_manual_report.py 渲染 HTML / PNG。

wechat-intelligence-hub
只读 Reader（wechat-cli）取数 → 本地情报引擎 → 同时输出 wechat_daily_full.md 与交互式 wechat_daily_report.html。

切走这一层，你就能把 任何来源 的数据塞进 任何模板：两个仓库的渲染器都是可替换件。

1报头：群名 / 时间窗 / 口径▸

报头只做三件事：说清这是哪个群、哪段时间、按什么口径统计。口径不写清，后面所有数字都可被质疑。

取数来自会话表（群名、群 ID）与消息表的时间字段；对应命令是 WeChatDaily 的 python wechat.py groups（先列群）与 intelligence-hub 的只读 Reader 列会话。

关键工程细节：不要跳过确认群名和日期。WeChatDaily 的 Skill 里专门写死了一条规则——即使用户已经给了群名和日期，也必须先拉群列表比对并回显确认。

来源：WeChatDaily wechat.py groups / export --date --groups；hub wechat-cli 只读 Reader

2四宫格指标：口径必须自洽▸

本页四个指标：
消息总量 = 窗口内消息条数；
活跃成员 = 去重后的发言人数；
话题提及 = 各话题命中次数之和（同一句话可命中多个话题，故大于消息数）；
待跟进线索 = 待回复 + 承诺 + 商机 + 复联，共 9 条。

最后一项直接对应 intelligence-hub 的四个线索桶：待回复 / 承诺 / 商机 / 复联线索——这是它比「纯总结」更有用的地方，总结完能落到行动。

📌 学习点：量纲要自洽。 原始参考图里「389 条消息」旁边挂着「5792」这种不同量纲的数字，读者第一反应是「这数怎么来的」。本页把它改成可从同一份数据反算出来的指标，报面才可信。

来源：hub 日报的「待回复 / 承诺 / 商机 / 复联」四类线索；WeChatDaily 的统计区块

3活跃时段与小时曲线▸

把消息按小时分桶，就得到一条「群聊成交量」曲线——这是「行情小报」这个比喻的落点：消息量 = 成交量，话题 = 板块，热度环比 = 涨跌幅。

配色沿用 A 股习惯：上涨用红、回落用绿。别照抄欧美配色，中文读者会看反。

峰值所在小时就是「活跃时段」，可以直接用于定时发布：在活跃时段前半小时推日报，打开率明显不同。

来源：消息时间字段分桶统计；定时发送见 WeChatDaily 的 schtasks 示例（每日 22:00 自动导出）

4热门板块卡：摘要必须能溯源▸

每张卡只有五样东西：话题标题、板块标签、热度环比、三行摘要、一句原话。热度 = 该话题提及数 ÷ 全部话题提及数，环比 = 与前一周期同窗口对比。

⚠️ 最容易踩的坑是「AI 一本正经地编」。解决办法是让模型在输出里带上来源消息 ID（本页 JSON 契约里的 sources 字段），渲染时挂回原消息链接——intelligence-hub 的 HTML 版默认支持点击跳回原文（原链接跳转），这就是可核查。

📌 布局取舍：参考图用双列密排（信息密度高、适合手机竖屏长图）；本页默认单列（利于阅读和讲解），顶部「密排双列」开关可以一键切回参考图那种排版。

来源：WeChatDaily analysis-prompt.md 结构化分析；hub 交互式 HTML 的原链接跳转

5发言排行：可以做，但要守边界▸

就是按发言条数排序 + 占比条。技术上零难度，难的是把它用在哪。

✅ 合理用法：判断谁是群里的内容贡献者，作为运营参考。
❌ 危险用法：拿去考核、公开点名、贴「潜水榜」。排行榜一旦变成人身评价，群就凉了。

建议做法：默认只统计发言量，不做「质量分」；涉及具体人时，把昵称脱敏成「群友 A / B / C」。intelligence-hub 的设计原则也写在明面上——微信相关能力只读，不发送消息、不操作 UI。

来源：hub 隐私与安全章节（只读、样例全虚构、报告不入 Git）

6落款：合规声明要印在报上▸

报面底部固定印三行：取数范围、统计口径、合规红线。这不是形式主义——日报一旦外发，读者必然要问「这些数据哪来的、有没有上传」。

标准答案就一句：本地解密、只读、数据不出本机。两个仓库都把这一点写在首页：WeChatDaily「聊天记录解密在本机完成，数据不出本机」；intelligence-hub「Reader 核心不获取密钥、不重签名、不注入、不 Hook 微信」。

另外，本页所有昵称、话题、金额均为虚构——这也是那两个仓库明文要求的：真实聊天、联系人、输出报告不得提交到 Git，仓库样例必须是虚构数据。

来源：两个仓库的隐私与安全 / 注意事项章节

JSON数据契约 analysis_*.json

报面所有元素都由这份结构驱动。换成你自己的数据，整张报面即变，一行 HTML 都不用改。

展开 JSON 结构 
// 这就是本页顶部那个 REPORT 对象
{
  "meta": {
    "group": "群名",  "date": "2026-09-10",
    "window": "11:00-12:00", "scope": "群聊文本"
  },
  "stats": [
    { "key": "消息总量", "value": 389, "unit": "条" }
  ],
  "hours": [ { "h": 11, "msgs": 52 } ],   // 24 项

    "mentions": 41,
    "delta": 0.06,              // 热度环比
    "summary": ["要点1","要点2","要点3"],
    "quote": "代表性原话",
    "sources": ["msg_id_1", "msg_id_2"]  // 可溯源
  }],

验证「数据与视图分离」

按 F12 打开控制台，敲：

REPORT.topics[0].title = "我改的标题";

A这条流水线怎么跑

四步。前两步决定数据能不能到手，第三步决定内容有没有价值，第四步决定好不好看。两个仓库的区别主要在第 1、2 步，第 3、4 步思路一致。

STEP 01

取密钥 · 本地解密

微信 4.x 的库是加密的，需要先拿到本机的 raw key，再解密出可读的 SQLite 库。整个过程在本机完成。

tools\wx_key\wx_key.exe → WX_RAW_KEY=64位hex python wechat.py decrypt
WeChatDaily：wx_key + WeChatDecrypt
hub：rion-wechat-reader（只读）
STEP 02

导出指定群 · 指定日期

按群名和日期把消息抽成结构化文本。建议拉全量（-limit 很大），否则话题会被截断。

python wechat.py groups python wechat.py export \ --date 2026-09-10 \ --groups 示例群 --limit 99999
输出：Markdown 聊天记录
STEP 03

Agent 结构化分析

让 AI Coding Agent 读记录，输出话题 / 热度 / 摘要 / 金句 / 来源 ID 的结构化 JSON。这是唯一的智能环节。

→ analysis_2026-09-10.json （Skill 在这步加载分析 Prompt）
WeChatDaily：内置 Skill
hub：$wechat-intelligence-hub
STEP 04

模板渲染成报

把 JSON 灌进模板。产出 HTML，需要长图再截 PNG。

render_manual_report.py → report.html + report.png （Chromium 截图）
本页就是这一步的产物

C复刻清单

想在自己机器上跑通同一条链路，按顺序做这五件事。左边是做对了的检查点，右边是必须避开的坑。

✓ 照着做

  • 先跑虚构 Demo：hub 提供全虚构样例，先验证索引与报告链路，再碰真实库
  • 键名与目录固定：WX_RAW_KEY 等写进 .env，不要硬编码进脚本
  • 导出拉全量：--limit 99999，否则长话题会被截断，摘要直接失真
  • 先脱敏再送 AI：昵称做映射，发出去的只有文本摘要
  • 让分析带来源 ID：每条摘要挂回原始消息，读者能自己核查
  • 定时只做导出：schtasks 每天 22:00 跑导出，分析+渲染留在有人确认的环节

! 别踩的坑

  • 别用 UI 自动化那批老项目：依赖 Hook / 注入的路线，微信版本一升级就全废，维护成本不可控
  • 别把 key 或数据库发人：两个仓库都明确说不要向维护者、社群、Issue 发送 key、密码和数据库
  • 别把真实记录提交 Git：.env、export/、解密产物全部 ignore
  • 别做「无人值守自动发消息」：只读是底线；涉及账号、支付、发布等外部写入动作，必须由人最终确认
  • 别把排行做成考核：发言量只用于运营参考，脱敏后再外发
  • 别让量纲打架：每个数字都要能反算出出处，报面才立得住
关于「科技风」的一点建议：科技风不是把背景调成黑色、加一堆发光边框。它靠三样东西成立—— 等宽字体承载数据（数字、时间窗、指标标签全部用 mono）、 颜色只承担一种语义（本页红=涨、绿=跌、青=强调，不再加第四种含义）、 留白建立层级（模块之间用虚线分隔，而不是靠更多卡片堆叠）。 把这三条守住，浅色底一样很科技。

D怎么接进你自己的链路

你手上已经有群消息通道和一套卡片渲染管线，所以最省力的做法不是装这两个工具，而是只借它们的「分析 Prompt + 字段契约」，渲染仍走你自己的模板。

方案一：只借分析层（推荐）

  • 保留你自己取数通道，输出当天的群聊纯文本
  • 移植 analysis-prompt.md 的思路，约束模型只输出 analysis_*.json
  • JSON 直接喂你现有渲染管线，产出 3:4 竖版长图
  • 产物顺手进你的素材库，可复用、可检索、可二次分发

方案二：装工具跑通全链路

  • WeChatDaily：Python 3.14+、Windows、微信 4.1+，需支持 Agent Skill 的 AI Coding 工具
  • hub：走 ./scripts/install.sh --with-sqlcipher，先跑虚构 Demo 再接入本机
  • 两者都是「先确认再执行」的接入流程，不是装完自动读全量历史
  • 适合先验证效果，再决定要不要自己重写一层
